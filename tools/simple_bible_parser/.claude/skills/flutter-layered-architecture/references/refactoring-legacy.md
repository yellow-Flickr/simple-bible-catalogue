# Refactoring Legacy Flutter Features

Improve one behavior boundary at a time. Preserve externally visible behavior
unless the task explicitly asks to change it. Do not impose a new architecture
or replace packages as a side effect of a focused migration.

## Recognize boundary problems

Common signals include:

- widgets own network, database, file, or platform calls;
- business rules are repeated in screens or hidden inside data adapters;
- one state object or service owns unrelated features;
- mutable state can be changed by arbitrary widgets;
- raw maps or transport response types cross the whole app;
- dependencies are constructed ad hoc or found through hidden global lookup;
- failure handling is inconsistent or errors are silently discarded.

These are prompts to investigate, not proof that every layer is needed.

## Incremental migration

1. **Trace behavior.** Find every caller, state owner, data source, side effect,
   and relevant test. Record existing success, empty, cancellation, and failure
   behavior.
2. **Choose a bounded feature.** Prefer a cohesive, low-risk feature with few
   consumers. Agree on the behavior to preserve.
3. **Isolate external I/O if useful.** Move transport or persistence behind an
   adapter with typed inputs and outputs. Keep the existing package and
   response semantics.
4. **Extract policy only when needed.** Add a use case/service for workflows,
   business rules, multi-source orchestration, or cache/error policy. Avoid
   adding a pass-through class solely for symmetry.
5. **Move presentation state.** Add or adapt a view model/controller using the
   existing state-management approach. Keep UI-specific state and safe error
   mapping there.
6. **Repoint callers gradually.** Update one screen/caller at a time and
   compare behavior. Keep compatibility adapters only when they enable a safe
   staged migration.
7. **Remove dead paths.** Once no caller uses legacy code, remove it and update
   documentation and tests.
8. **Verify and stop.** Run focused tests, analysis, and formatting. Keep the
   change limited to the agreed feature.

The order can change to fit the codebase. For example, a local-only screen may
need a controller before any repository, while a mature data adapter may be
reused as-is.

## Split a god object

1. Inventory state and methods, then group them by feature and lifetime.
2. Select a cohesive group with manageable consumers.
3. Move its state and operations to the new owner.
4. Migrate consumers incrementally and verify there is one source of truth.
5. Remove the old fields/methods only after their callers are gone.
6. Repeat only while the remaining object still has unrelated
   responsibilities.

Avoid making old and new objects independently mutable during the transition.
If a compatibility surface is needed, make it delegate to the new owner and
mark it for removal.

## Preserve correctness during cutover

- Guard against duplicate requests or repeated side effects where required.
- Preserve cancellation and empty-result semantics. Check nullable or empty
  selections before indexing or reading a file.
- Ensure loading state and resources are restored when operations fail.
- Keep auth, permissions, and tenant context consistent across migrated calls.
- Do not log sensitive data or introduce secrets into examples or source.
- Keep generated code generated by the project's tooling.

## When to stop

The refactor is complete when the agreed behavior is preserved, ownership is
clearer, the new boundary is used by its callers, and focused validation
passes. Avoid unrelated renames, broad package migrations, visual redesigns,
or speculative abstractions in the same change.
